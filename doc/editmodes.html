Edit Modes

J has two ways of reading the keyboard. In the default simple edit mode every key means itself: a printable character that no key map claims is inserted into the buffer. In vim edit mode the keyboard is modal, as it is in vi and its descendants: a key means one thing while you are typing text and another while you are giving commands.

Note that "edit mode" and mode are different things. A buffer's mode is the language it holds -- Java mode, HTML mode. Its edit mode is how the keyboard behaves.

Turning it on

Add this to your preferences file: 

    editMode=vim

Like any other preference it can be set for one mode only: 

    JavaMode.editMode=vim

Only ordinary text buffers are affected. Directory buffers, image buffers and the like bind plain letters as commands of their own and are always in simple edit mode.

What is there

Normal, insert, visual and visual-line modes, operator-pending commands, counts, registers, marks and the dot command:
motions h j k l 0 ^ $ w W b B e E ge gE gg G | f F t T ; , { } % H M L and the arrow keys
operators d c y > < gu gU g~, doubled for whole lines (dd, cc, yy)
changes x X D C s S r R J gJ ~ p P
insert i I a A o O, leaving with Escape
visual v V o gv, and any operator over the selection
registers "a through "z (upper case appends), "0, "1-"9, "-, "_
marks m, `, ', ]`, [`, ]', [', and `< / `> after a selection
other u, Ctrl R, .

Counts work where vim's do, and multiply across an operator and its motion: 2d3w deletes six words. An insert session is one undo step, so u after cwsomething<Esc> puts back both what went and what came.

What is not there yet

Text objects (iw, i(), searching (/, ?, n, *), the : command line, visual block mode, macros (q, @), and the insert-mode commands (Ctrl W, Ctrl R).

A key that vim mode does not claim falls through to j's own key maps, so Ctrl S still saves and Alt X still prompts for a command.

Changing the bindings

The bindings are not built into j: they are read from a table, and you can replace it or override parts of it.

The table

The built-in table ships as default-keymap.conf inside j. Each row is a binding: 

    # modes  keys            kind      command           args
    n,v,o    w               motion    moveByWords       forward
    n,v,o    f<character>    motion    moveToCharacter   forward,inclusive
    n,o,v    d               operator  delete            -
    n        i               action    enterInsertMode   at=here,isEdit
    n        x               keytokey  dl

modes are the letters vim's map commands use: n normal, v visual, o operator-pending, i insert. keys is the key sequence in vim's notation; <character> stands for any one key, which is how f waits for the character to find. kind is one of motion, operator, action, keytokey, command or idle. args are comma separated, either name=value or a bare name meaning true, or - for none.

To replace the whole table, copy it and set: 

    vimKeyMap=/home/you/.config/j/vim-keymap.conf

Your vimrc

To change a few bindings rather than all of them, put them in ~/.config/j/vimrc in the form you already know: 

    " j reads the parts of a vimrc it understands and ignores the rest.
    let mapleader = ","
    set shiftwidth=4

    nnoremap Y y$
    vnoremap < <gv
    nnoremap <leader>w :save<CR>

map, nmap, vmap, xmap, omap and imap are understood, with their noremap and unmap forms, along with set and let mapleader. A right-hand side that begins with : and ends with <CR> runs one of j's own commands, which is how a key reaches something the modal layer knows nothing about.

Anything else in the file -- vimscript, plugins, autocommands -- is reported in the log and skipped, so an existing vimrc can be pointed at j without being cut down first.

When a key is both a command and the start of a longer mapping, the longer one wins if you type it; otherwise the shorter one runs as soon as the next key shows it was not coming. Nothing is decided on a timer.

Where it differs from vim

These are known and deliberate:

  • > and < shift by j's indentSize unless a vimrc sets shiftwidth, and the indent they produce follows j's useTabs.
  • Registers are not shared with j's own kill ring or its file-backed registers. "+ and "* are not connected to the system clipboard yet.
  • Marks are per editor rather than per buffer.
