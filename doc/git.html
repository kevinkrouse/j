Git

j shows a repository's state in a status buffer, as magit and Neogit do: what has changed, what is staged, and the recent commits, with each file's diff inline. j runs the git on your path for it, version 2.16 or later. To see the commands it runs, use vcsCommandLog ($ in the status buffer).

The status buffer

gitStatus, mapped to Ctrl Alt G, and to <leader>gg in vim edit mode, opens the status of the current file's repository. In a project whose directory holds several repositories, it shows them all, each under a heading in its own color. 

Head:     main  1a2b3c4 icons: draw at the window's device scale
Upstream: origin/main  ↑2 ↓0

Untracked files (1)
  ?  notes.txt

Unstaged changes (2)
  M  src/Display.java
  @@ -60,6 +60,12 @@ class Display
  ...
Staged changes (1)
  A  doc/git.html

Recent commits (10)
  1a2b3c4 (HEAD -> main, origin/main) icons: draw at the window's device scale

The sections are those that have something in them: unmerged files during a merge, untracked files, unstaged changes, staged changes, and the recent commits. A line under the header says when a merge, a rebase or a cherry-pick is in progress, and how many conflicts it has.

A dimmed row over the first line shows the main keys, in the notation of the edit mode you are in; vcsHints turns it off. ? opens a popup of the rest, and F1 this page.

Showing and hiding

A section, a file and a hunk each open and close: Tab on one, or on a line in it, toggles it, as does a click on the chevron in the gutter beside it. A file starts closed; opening it reads its diff. Shift Tab steps everything through four depths, and 1 to 4 go to one: 1 shows the sections, 2 their files, 3 the files' hunks, and 4 every line of the diffs. In vim edit mode za, zo and zc toggle, open and close, and zR and zM open and close everything.

In a diff, the words that changed in a line are on a stronger shade than the rest of it, when a removed line and the added line that replaces it have enough in common.

Moving and visiting

n and p go to the next and previous thing that opens, or commit; Alt N and Alt P, and ]] and [[ in vim edit mode, to the next and previous section. Enter, or a double click, visits the thing at the caret: a file, at the line of the hunk or diff line the caret is on, or a commit, shown with its diff. A staged line is visited where it is now, after the changes made since it was staged.

Refreshing

The buffer is read again when the repository's index, HEAD or branches change, when you save a file, and when j's window comes back to the front. g (r in vim edit mode, where gg goes to the top) reads it again now, for a change j could not see. Reading it again keeps the caret on the file or line it was on.

Staging and discarding

s stages the thing at the caret, u unstages it, and x discards it: a section heading's files, a file, or the hunk the caret is in. With a selection, they take what it covers, down to single lines of a hunk: select the lines to stage and press s (in vim edit mode, V or v and then s). A changed line is its removed line and the added one that replaces it: selecting either takes both, so the change is staged and not the new line beside the old. S stages every change to a tracked file, and U unstages everything.

Discarding asks first, naming what is lost. An unstaged change goes back to what is staged; a staged one comes out of the index and the working tree both, unless the file has unstaged changes in the same lines, when nothing is done and the status bar says so. A file no commit has, untracked, added or noted with git add -N, goes whole: to the desktop's trash, or deleted where there is none. A staged rename is unstaged (u) before it is discarded. s on a conflicted file marks it resolved, after asking.

While one change is being made, and until the buffer shows it, another waits: the status bar says so.

git runs in the background. When a command fails, the status bar says why and the command log opens with its output.

Committing

c opens the commit popup. Its switches are -a to stage every change first, -e to allow an empty commit, -n to skip the hooks, -s to sign off, and -v to show the diff being committed under the message, as git commit -v does; git's commit.verbose setting turns -v on too. Ctrl S in the popup keeps the switches as the defaults. Then:

  • c commits what is staged, with a message you write;
  • a amends the last commit, starting from its message;
  • e extends it with what is staged, keeping its message;
  • w rewords it, leaving what is staged as it is.

The message opens in a window beside the status, under the files it commits, as # lines that are left out of it. In vim edit mode it starts in insert mode. A summary line past 50 characters, and any line past 72, show where they run over. With -v, the diff is under a scissors line, and nothing from that line down is in the message. Ctrl Enter commits; Escape (in vim edit mode, in normal mode) gives the message up, asking first. In vim edit mode ZZ and :wq commit too, :q gives the message up asking first, and ZQ and :q! without asking. Ctrl P steps back through the messages committed or given up before, and Ctrl N forward again to the one being written. A message can't be closed while it is being committed, and one whose hooks fail is kept for another try.

Change marks in the editor

In a file git tracks, the change marks beside the lines are git's, in place of j's own marks of what changed since the file was loaded: a green bar for a line added, a blue one for a line changed, and a red triangle where lines were deleted, against what is staged. A change that is staged keeps its mark, dimmed, until it is committed. They are worked out again as you type, a moment after you stop, and when the repository changes. vcsSigns turns them off, and a file git does not track keeps j's marks.

The commands of Change Marks work on git's changes: nextChange and previousChange go by them, revertLines puts one back as it is staged, and previewChange shows it against what is staged, or the staged change there when there is no other. On the change at the caret, or the lines of the selection, too:

  • vcsStageHunk (<leader>hs) stages it, as the buffer has it, saved or not;
  • vcsUnstageHunk (<leader>hu) takes a staged change back out of the index.

The preview's bar and the popup a click on a mark opens have these too.

The buffer list

The buffer lists in the sidebar, and the Ctrl E switcher, show a file's status after its name: M changed, M in green staged, A added, ? untracked, D deleted, R renamed, C copied and U conflicted. gitBufferListStatus shows a dot instead, or nothing. When the project has several repositories, a strip at the left of a row is its repository's color.
