# Conformance cases that are expected to pass, one name per line.
#
# A ratchet: a name is added when a milestone implements the feature that case
# covers. If a listed case stops passing the build fails. Cases not listed are
# free to fail while the modal engine is still being built --
# VimConformanceTest prints any that start passing.
#
# Promotion is deliberate, never automatic. A case whose expectation is "the
# document did not change" passes for the wrong reason while normal mode is
# still swallowing keys it does not understand, so these are left out even
# though they currently pass: Y, s_visual, *_no_word and
# jumpToMark_next_sameline all test features that do not exist yet.
# r_visual_block with surrogate characters is held out the same way: <C-v>
# is not built, so it passes as a plain ru.
# (ex_sort_oneline and ex_sort_pattern_alpha_reverse were held out for this
# reason until M12b built :sort; they are listed below now that they pass
# for the right one.)
#
# Cases where nvim disagrees with the CodeMirror corpus, verified with
# tools/vim-oracle.sh. nvim wins, so these stay out of passing.txt and are
# not bugs to chase:
#
#   dge_start_of_document   corpus deletes a char; nvim does nothing, because
#                           ge at offset 0 has nowhere to go
#   dge_empty_lines         the corpus leaves "\n"; nvim leaves "". The range
#                           runs from blank line to blank line, and :help d
#                           makes such a delete take the lines whole
#   dw_repeat               same rule: d2w from " word1" over "word2" has only
#                           blanks before it and nothing after, so nvim takes
#                           both lines and leaves "", not the corpus's " "
#   %_skip_string           its first half passes. The second starts on the )
#                           inside ")" and expects the ( at 0; nvim fails
#                           there and stays put, because a quote lies between
#                           the two brackets
#   dj_end_of_document      corpus deletes the line; nvim needs two lines for
#                           dj and does nothing on a one-line buffer
#   dk_start_of_document    same, upward
#   * # g* (second halves)  the corpus expects Match to match match, which
#                           needs ignorecase; vim defaults to noignorecase
#                           and nvim agrees with us
#   ex_sort_decimal*        the corpus spells the numeric sort flag "d"; vim
#   (five cases)            spells it "n" and rejects "d" outright. Our "n"
#                           gives exactly what these cases expect of "d"
#   ex_sort_pattern_alpha_  the corpus reverses only the lines the pattern
#   only_reverse            matched, keeping the rest in their original
#                           order. nvim reverses the whole result, and so do
#                           we: c b a3 y2 z1, not c b z1 y2 a3
#   delmark_multi           :delmarks is right in all three -- a deleted mark
#   delmark_multi_space     stops working and the others keep working. They
#   delmark_range           fail on their last assertion, which puts a mark
#                           at column 2 of an empty line and expects to come
#                           back to it. CodeMirror lets the caret sit past
#                           the end of a line; vim and j do not, so the mark
#                           is at column 0
#   /_greedy                the corpus writes its patterns in JavaScript's
#   ?_greedy                regex syntax, where + means one-or-more. In vim's
#   ex_sort_pattern_alpha_  default magic level a bare + is the character, so
#   longer                  /a+ finds nothing and sort r/[a-z]+/ leaves the
#                           lines as they were -- nvim does both, and so do
#                           we since M12.5. The vim spellings /a\+ and
#                           sort r/[a-z]\+/ give exactly what these cases
#                           mean, and are unit tested. These three passed
#                           before M12.5 for the wrong reason: Java's regex
#                           syntax happens to agree with JavaScript's.
#   ex_global_substitute_   the corpus writes \n in a replacement to break the
#   split                   line. In vim that inserts a NUL; \r is the line
#                           break. nvim leaves NULs where the corpus expects
#                           new lines, and so do we since the M12.5 review.
#                           The same :g with \r is unit tested.
#   macro_last_ex_command_  our text is right (2@: gives bbbaa) but the
#   register                corpus wants the caret at column 2. Vim leaves it
#                           on the first non-blank of the changed line: 0,0
#                           here, and 0,4 on an indented line, whatever
#                           column the match was in. Confirmed with nvim on
#                           a plain :s, since @: cannot run inside :normal!
#   S_normal                the corpus expects S then Escape to leave the
#                           line's indent behind. nvim ('autoindent' on)
#                           takes an indent nothing was typed after away
#                           again, leaving an empty line, and so do we. Sx
#                           keeps it: "  x". Unit tested in VimM13Test
